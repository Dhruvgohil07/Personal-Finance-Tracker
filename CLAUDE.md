# Kharcha — Personal Finance Tracker

A personal finance tracker: users upload bank statements (CSV/PDF), and the app
produces categorized spending, subscriptions, budgets and alerts.
Backend: Python 3.12 + FastAPI + PostgreSQL + SQLAlchemy/Alembic + RQ/Redis.
Frontend (Phase 3+): Next.js in plain JavaScript.

The full specification is in `docs/SPEC.md`. Before starting any task, read the
SPEC.md sections relevant to it (e.g. §5 Data Model for a new table, §6 for
parsing work, §10 for a new endpoint). The rules in THIS file apply to every task.

## 4. Core Engineering Rules (always follow)

1. **Money is never a float.** Store all amounts as integer paise in `BIGINT` columns (₹12.50 → `1250`). Parse statement strings with `decimal.Decimal` and convert to `int` paise; never use `float()`. Helpers live in `app/utils/money.py` with thorough tests (commas, `Cr`/`Dr` suffixes, negatives in brackets, blank cells).
2. **Every query is scoped by `user_id`.** No endpoint may return or modify another user's data. Write an integration test proving cross-user access (IDOR) returns 404.
3. **Never log sensitive data:** no raw narrations, amounts, balances, statement passwords, tokens, or file contents. Log IDs and counts only. Configure a structlog processor that redacts known sensitive keys.
4. **Statement passwords are never persisted** — not in the DB, not in Redis/RQ job arguments, not in logs (see §7.2).
5. **Imports are idempotent.** Uploading the same statement, or overlapping statements, must never create duplicate transactions (see §6.3 in `docs/SPEC.md`).
6. **Business logic lives in services / pure modules**, not in route functions. Routes only validate input (Pydantic), call a service, and return a response model.
7. **Migrations are append-only.** Never edit a committed Alembic migration; create a new one. Review autogenerated migrations before applying.
8. **Never commit real bank statements.** Test fixtures must be synthetic or fully anonymized.
9. **Record significant design decisions** as short ADRs in `docs/decisions/` (context → decision → alternatives rejected → consequences).
10. Dates: statement dates are stored as `DATE` (no time). App timezone is `Asia/Kolkata`. Money is displayed in Indian format with lakh grouping (e.g. ₹1,25,000.00) — provide a formatter.
11. Use type hints on all functions; use Pydantic models for all API input/output (never return raw ORM objects).

## 7. Security & Privacy (core feature)

### 7.1 Auth
- argon2id password hashing; minimum password length 8
- Access JWT (15 min) returned in the response body; refresh token in an httpOnly, Secure, SameSite=Strict cookie; rotation on every refresh with family-based reuse detection
- `get_current_user` FastAPI dependency protects all non-auth routes
- Rate limits (slowapi): login/register 5/min/IP; uploads 10/hour/user; general API 100/min/user
- Generic error message on login ("invalid email or password")

### 7.2 Statement passwords
- Accepted only on the upload request (or `POST /uploads/{id}/password`), used in memory, then discarded
- Never written to DB, Redis/RQ job arguments, logs, or error messages. Add a test asserting the enqueued job's arguments contain only the upload id.

### 7.3 Data protection
- Uploaded files encrypted at rest (AES-256-GCM, key from env `FILE_ENCRYPTION_KEY`) and deleted after processing
- Only last 4 digits of account numbers stored; strip account numbers from narrations before any LLM call
- `DELETE /me` performs a hard delete of all user data (cascade) and writes a final audit entry
- Export: user can download all their transactions as CSV
- Security headers via a small middleware (X-Content-Type-Options, X-Frame-Options, Referrer-Policy, etc.); strict CORS (only the frontend origin) via FastAPI's CORSMiddleware
- Pydantic validation on every input; upload size limit enforced
- Parameterized queries only (SQLAlchemy ORM / `text()` with bound params) — never build SQL with f-strings

### 7.4 AI privacy
- User setting `ai_enabled` (default true, clearly explained in Settings); if false, the LLM step is skipped entirely
- Send only the normalized merchant string (no amounts, no names of individuals, no account numbers, no dates)
- Person-to-person UPI transfers are never sent to the LLM (see §8.3 in `docs/SPEC.md`)

### What to do at the end of each task
1. List exactly which files belong to this task, so I can stage them (e.g. `git add backend/app/utils/money.py backend/tests/unit/test_money.py`). Never suggest `git add .` or `git add -A` without listing the files.
2. Confirm that nothing sensitive is being staged: no `.env`, nothing from `samples/`, no exported CSVs, no real statement data.
3. Propose a commit message following the format below. I will review it and commit it myself.

### Commit message format (Conventional Commits)
```
<type>(<scope>): <short summary>

<body: what changed and why, wrapped at ~72 characters>
```
- `type`: one of `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `ci`, `build`, `perf`
- `scope`: the area touched, e.g. `money`, `auth`, `parsers`, `db`, `api`, `worker`, `ci`
- Summary: imperative mood ("add", not "added"), lowercase, no trailing period, max 72 characters
- Body: explain **what** changed and **why** (the reasoning a reviewer or interviewer would ask about). Skip the body only for trivial changes.
- One logical change per commit. If a task naturally splits into two changes, propose two commits.

Examples:
```
feat(money): add paise parser and INR lakh formatter

Parse statement amounts with Decimal into integer paise to avoid
float rounding errors. Handles commas, Cr/Dr suffixes, bracketed
negatives and blank cells. Formatter outputs Indian grouping
(e.g. ₹1,25,000.00).
```
```
fix(parsers): handle multi-line narrations in HDFC PDF statements
```

### No AI attribution — ever
Commit messages must NEVER contain:
- `Co-Authored-By:` lines of any kind
- "Generated with Claude Code" or similar footers
- Emojis added as signatures, or any mention of Claude, Anthropic, or AI tools

This also applies to PR titles/descriptions and any other text you draft for git or GitHub.
